## Check the public response first

Open representative pages without relying on client-side interaction and confirm that useful text and links are present. Check status codes as well as appearance. A missing page should return a genuine not-found response, while a moved page should redirect to a relevant destination. A page showing an error message with a success status creates ambiguity for visitors and crawlers.

Inspect production configuration for accidental noindex directives, authentication gates or crawler blocks. A staging environment and a public launch have different requirements. Review hosting and CDN settings alongside application files, because a permissive robots file cannot override an upstream access block. Keep private records protected by access controls rather than assuming a robots rule provides security.

## Make metadata specific to each page

Write a title that identifies the page's main purpose and a description that explains its value honestly. Avoid repeating the same generic description across services and articles. Match the main heading to the visible topic without forcing identical wording everywhere. Character-length targets are useful editorial checks, not guarantees that a search engine will display the text unchanged.

Check the rendered title, description, social image and canonical URL. If a page is generated from content, validate the output after generation. Social previews should use absolute URLs and images with dimensions. A default layout title can conceal missing page metadata, so review every indexable route rather than assuming the template covers all cases.

## Choose a consistent canonical URL policy

Decide the preferred HTTPS host and trailing-slash convention. Redirect alternate public variants consistently and use the same canonical URLs in internal links and sitemaps. Preserve established URLs where possible during redesigns. If a URL must change, map it to the most relevant new destination rather than redirecting every old page to the homepage.

Canonical links express a preference; they do not repair every duplication or access problem. Check that the preferred URL returns the intended content and can be indexed. Keep query parameters used for tracking out of unnecessary duplicate links. Language alternates should describe actual translations, not countries where the business hopes to acquire customers.

## Build navigation around useful content

Link important services from the homepage and connect detailed guides with relevant services and evidence. Use descriptive anchor text that makes sense before someone follows it. Breadcrumbs help visitors understand where a page sits, while related reading gives a practical next step. Do not create isolated pages that exist only inside the sitemap.

Review links after content changes and include an accessible footer map of key sections. For a long blog, use crawlable archives and pagination rather than relying entirely on a JavaScript search interface. Check local fragment links as well as page URLs. A table of contents is useful only when its links reach the intended headings.

## Publish evidence and direct answers

Explain what the business does, where it is based and how to contact it consistently. Add case-study detail only where there is evidence. A screenshot can support a description of an interface; it does not establish a measured conversion improvement or a customer endorsement. Leave unknown founder details, rates and performance claims unpublished until confirmed.

Write short direct answers to common customer questions, followed by the context needed to make a decision. Use real tables for comparisons and lists for processes. Include an author or publisher and meaningful revision dates. Do not update dates automatically on every build, because that suggests an editorial review that may not have occurred.

## Keep structured data aligned with visible text

Describe the organisation, website, services, breadcrumbs and articles using accurate structured data. FAQ answers should match what readers can access on the page. Do not add invented reviews, ratings, prices or personal authors to satisfy a checklist. If site search does not exist, do not describe a search action that visitors cannot use.

Validate JSON syntax and the relevant required fields, then use external rich-result tools where appropriate. Passing a JSON parser is not the same as qualifying for a search feature. Search engines and answer engines decide whether and how to use the information. Treat schema as a clear description of evidence, not a placement mechanism.

## Check images, fonts and mobile interaction

Give meaningful images useful alternative text and reserve their dimensions to reduce layout movement. Use suitable formats and sizes, load below-the-fold images lazily and prioritise the actual largest-content element where appropriate. Avoid preloading every image or font. A preload consumes resources, so it should support a demonstrated critical dependency.

Test keyboard navigation, form labels, focus visibility, heading order and reduced-motion behaviour. Measure a production build on mobile conditions rather than relying on a desktop development session. Laboratory scores and field experience answer different questions. Keep heavy scripts and integrations under review, especially when they are not necessary for the visitor's main task.

## Set up measurement and monitoring

Verify ownership in the relevant search consoles and submit the sitemap. Inspect representative URLs and monitor coverage after launch. Configure analytics only with the intended measurement account and respect the site's consent choices. Keep personal details out of event names, parameters and page URLs sent to general analytics.

Track useful actions such as confirmed enquiries, calls and contact clicks with clear definitions. A click is not proof of a completed sale, and a form animation is not proof that a message was delivered. Review failures and customer feedback alongside search data. Use measurement to identify the next useful improvement instead of promising a ranking or citation outcome.

## Use a launch and maintenance checklist

1. Verify public status codes and crawler access.
2. Check unique metadata, headings and canonical URLs.
3. Validate navigation, archives and sitemap coverage.
4. Confirm visible business facts and structured data.
5. Test mobile performance, accessibility and forms.
6. Verify consent, events and search-console ownership.

Repeat relevant checks when adding pages, changing templates or connecting new providers. The [website maintenance guide](/blog/website-maintenance-guide) explains ongoing responsibilities. Bring unresolved technical issues to the [digital marketing service](/services/digital-marketing) with concrete examples. A useful SEO foundation supports accurate content and reliable operation over time; it does not replace either of them.
